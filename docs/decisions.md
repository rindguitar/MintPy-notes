# 設計判断の記録

## 2026-10-11: 開発環境は専用の conda 環境 `mintpy` に、CI 相当のパッケージで作る
- 決定: `mamba create -n mintpy --file requirements.txt gdal libgdal-netcdf pre-commit pyfftw pytest setuptools_scm` → `pip install -e ~/MintPy`
- 理由: CI（`.circleci/config.yml`）と同じ範囲にしておけば、手元で通ったものが CI でも通る。環境名は isce3 と揃えてプロジェクト名にし、依存の衝突を避けるため isce3 環境とは分ける
- 却下した代替案:
  - installation.md 例示の環境名 `insar` → 何の環境か分かりにくい
  - `isce2` も追加 → ISCE-2 の出力を自分で処理する予定がなく、CI も入れていない。依存が重い
  - `requirements.txt` + pytest + pre-commit のみ → ARIA / HyP3 / GMTSAR の統合テストが動かない
  - path setup 方式（`PYTHONPATH` を通す）→ installation.md で非推奨寄り。entry point が登録されない

## 2026-11-24: #850 の PR は draft ではなく通常の PR にし、`Fix #850` を付ける
- 決定: 下の 2026-11-22 の判断のうち、draft の部分を変更する。手元で検証・pre-commit・テストまで済ませてから、通常の PR（本文に `Fix #850` と「方針について意見があればください」）を出し、#850 に PR 番号を添えてコメントする
- 理由: 方針はメンテナ自身が #850 で示したものと、本体（`coord.py` / `resample.py`）のやり方に沿っていて、変更も小さい。安全さは draft にすることではなく、出す前の手元での検証で確保する。MintPy では通常の PR が普通（open な draft は 0 件）
- `Fix #850` について: マージされると #850 が自動で閉じるが、閉じるかどうかはマージするメンテナの判断。後で近い問題が見つかったら、新しい issue を立てて #850 や PR を参照する
- 投稿（PR の作成と #850 へのコメント）はメンターの go のあと

## 2026-11-22: #850 は新しい issue を立てず #850 にコメントし、draft の PR を出す
- 決定: 新しい issue は立てない。修正を draft の PR（本文に「Fix #850」と「方針について意見がほしい」）で出し、#850 に PR 番号を添えてコメントする。意見をもらって直してから「Ready for review」にする
- 理由: CONTRIBUTING.md に「合う issue が既にあれば、そこにコメントして何をするつもりか知らせる」とある（公式の決まりを守る）。PR を出せば一覧で目立つので、古い issue に埋もれる心配は小さい。draft にして先に意見をもらうほうが、初めての PR として安全
- 却下した代替案:
  - 新しい issue を立てる → #850 と原因が同じで重複になり、経緯も 2 か所に分かれる
  - 最初から通常の PR → 修正は 2 行で検証もできるが、方針への意見を先にもらうほうを選んだ
- 補足: MintPy では 2026-11-22 時点で open な draft の PR は 0 件。draft は「作者の作業が途中」の合図なので、本文で意見がほしいことを明記する。#850 と原因が違う問題（出力の NaN を `geocode.py` が読めない件、緯度経度を画素の角で計算している件）は、必要なら別の issue にする

## 2026-11-05: #850 は「読むときに番号を直す」方法で修正する
- 決定: `lookup_geo2radar.py` の `run_lookup_geo2radar()` で、0（データなし）を除いたあとの `xx` / `yy` から、`-w` のファイルの `SUBSET_XMIN` / `SUBSET_YMIN` を引く（2 行の追加）。ファイルの中身や対応表の値は書き換えない
- 理由: MintPy 本体（`coord.py`、`resample.py` の 4 か所）と同じやり方で、対応表は切り出し前の基準のまま使える。緯度経度の値は変わらず、書き込む画素の番号だけが正しくなる
- 却下した代替案:
  - 出力を切り出し前の大きさで作る → 同じファイルの `height`（254 × 257）と大きさが合わず、同じファイルに入れられない
  - 対応表の値そのものを切り出し後の番号に書き換える → `coord.py` と `resample.py` が読むときにも引くので、二重に引くことになる

## 2026-10-11: CLAUDE.md のコーディング規約・Git規約は notes 用とし、`~/MintPy` では upstream の流儀に従う
- 決定: 日本語コメント・`feature/` ブランチ・`feat:` 接頭辞はこのリポジトリだけに適用する。`~/MintPy` のコードは英語のコメント・docstring、ブランチ名とコミットメッセージは CONTRIBUTING.md と既存の履歴に合わせる
- 理由: upstream は英語のコードベースで、コミットも `load_data: ...` のような形式。notes の規約のまま PR を出すと差し戻される。日本語での流れの説明は会話か notes 側で行えば「自分で説明できるコードだけ採用する」方針は保てる

## 2026-10-11: コントリビュートの題材は「内容に踏み込んだもの・既存 issue への貢献」を優先する
- 決定: ライブラリの新しい版で非推奨になった書き方の対応（警告つぶし）は題材にしない。見つけた問題は notes の Issue に記録し、upstream に出すかは別途判断する
- 理由: 非推奨対応はオーナーも把握していると考えられ、貢献としての価値が低い。InSAR の処理内容に踏み込んだものや、既存 issue の再現・原因調査のほうが upstream の役に立つ
- 却下した代替案: 統合テストで見つけた警告 3 件をそのまま PR にする → 1 件（#1）は実際に落ちる条件を再現できたので記録は残すが、優先はしない
